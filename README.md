# Two-legged walker

## Environment setup

Use Python 3.12. From the project directory, create a virtual environment and install the pinned dependencies:

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -r requirements.txt
```

The versions match the existing development environment. Opening a viewer requires a graphical desktop with OpenGL support.

Use the project virtual environment:

```sh
.venv/bin/python train.py --timesteps 1000000
.venv/bin/python watch.py
.venv/bin/python -m unittest test_walking_env.py
```

Training resumes `walker2d_both_legs_30kg_torso15_ankle10.zip` if present, otherwise starts a fresh PPO policy. Older checkpoints are preserved. The new policy has five extra observations for reward memory and cannot load the older checkpoint directly.

`walking_env.py` keeps Walker2d's forward movement, health, and control effort rewards, and adds:

- A penalty of 1 per unused foot per simulation step after that foot has not touched the floor for 1 second.
- A bonus up to 0.5 for changing the supporting foot, after 0.15 seconds of continuous single-foot support. The first support earns no bonus. The bonus is multiplied by forward velocity clipped to [0, 1], so standing or moving backward earns no switch bonus.

Tune `unused_after`, `unused_penalty`, `switch_bonus`, and `min_support_time` in `BothLegsReward` to change these incentives. They encourage both feet to participate but do not enforce a natural gait; contact tapping or shuffling may still emerge. Evaluate behavior in the viewer after training.

The viewer uses the same reward wrapper and observation shape as training. Per-worker Monitor CSV files under `logs/<model-name>/` record episode returns and lengths. Model files, the virtual environment, and generated logs are ignored by Git.

## Joint strength limits

The XML caps commanded motor torque at +/-100 Nm for hips and knees and +/-10 Nm for ankles, using normalized controls in [-1, 1] and motor gears of 100 and 10. This is a deliberately weaker ankle setting, not a calibrated human muscle model. There are no separate toe joints, muscle fatigue, or muscle force-length/velocity dynamics. Passive forces and contact forces are not capped by the motor torque limit.

Change the two foot motor `gear` values in `walker2d_separated.xml` to tune ankle strength. Training and viewing share this XML. A separate checkpoint starts training fresh for the changed dynamics and preserves previous policies. Reduced ankle torque limits ankle-driven propulsion but does not guarantee that hopping disappears.

## Body weight

Total body mass is 30 kg: torso 15 kg, each thigh 4 kg, each lower leg 2.5 kg, and each foot 1 kg. Explicit geometry masses replace the previous uniform-density distribution. MuJoCo infers each segment's inertia from its geometry and assigned mass. Gravity remains 9.81 m/s² downward; hip/knee and ankle torque limits remain 100 and 10 Nm. This is a simplified tuning experiment, not a calibrated human anatomical model.

The torso-weighted body has its own checkpoint. If the previous 30 kg policy exists when this change is applied, it is copied to seed the new policy while preserving the original. Further training is needed to adapt to changed dynamics. Redistributing mass does not guarantee a natural gait.

## Four-legged experiment

```sh
.venv/bin/python train_quadruped.py --timesteps 1000000
.venv/bin/python watch_quadruped.py
```

Independent Ant-v5 baseline: four articulated legs, eight joint motors, free 3D torso, local `quadruped.xml`, and separate `quadruped_ant.zip`. A fresh policy is required because action and observation spaces differ from Walker2d. Ant's default rewards encourage forward movement and health and penalize effort and contact forces. No custom four-leg gait reward is included. The body uses original Ant masses (about 0.91 kg), not the biped's 30 kg mass or ankle limits. Those need separate tuning for this body. Both viewers share pause, exit, overlay fixes, and episode statistics. Before training, the quadruped viewer shows zero actions.

## Windows with an NVIDIA GPU

Use Python 3.12 and run from the cloned repository in PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
```

Install CUDA-enabled PyTorch using the command generated by the [official PyTorch selector](https://pytorch.org/get-started/locally/) for Windows, Pip, Python, and a CUDA version compatible with your NVIDIA driver. Use `.\.venv\Scripts\python.exe -m pip` in place of `pip` in that command. Then install the other project dependencies (this file does not pin PyTorch, so the selected CUDA build is retained):

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-base.txt
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -c "import torch; print(torch.__version__, torch.version.cuda); print('CUDA available:', torch.cuda.is_available())"
.\.venv\Scripts\python.exe train_quadruped.py --device cuda --n-envs 8 --n-steps 1024 --batch-size 512 --timesteps 1000000
```

Use `train.py` for the biped. NVIDIA drivers alone do not ensure a CUDA-enabled PyTorch install. Explicit `--device cuda` fails with an actionable error if CUDA is unavailable; `--device auto` selects CUDA when available and otherwise CPU. Both scripts default to one simulation environment. MuJoCo simulations run on CPU; CUDA accelerates the policy network only. PPO's small MLP may be faster on CPU: compare reported training FPS using `--device cpu` and `--device cuda` with otherwise identical settings. Start with 4–8 workers, capped at your logical CPU core count. More workers are not always faster.

`--n-steps` is the rollout length per worker; total rollout size is `n-steps * n-envs`. Batch size must evenly divide that total. `--timesteps` counts combined steps across all workers, not steps per worker. `--torch-threads` defaults to 1 to limit CPU contention. Workers use Windows-compatible `spawn` under a main guard. Run the scripts from a terminal rather than executing them inside a notebook.

Existing policies resume on the chosen device with the requested rollout and batch settings. Use `--model-path experiment.zip` to start an independent experiment without overwriting the existing policy. `--save-every` defaults to 100000 total simulation steps; snapshots and worker logs are under `logs/<model-name>/`. Ctrl+C saves the current policy when the training loop catches the interrupt. Checkpoints omit unfinished rollout buffers and do not exactly reproduce the interrupted trajectory. Model and log files remain outside Git. No Windows/CUDA performance benchmark has been run on the macOS development machine.
